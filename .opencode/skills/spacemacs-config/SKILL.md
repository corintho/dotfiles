# Spacemacs config

## Hard rule

Never hand-edit `files/spacemacs/init.el`. It is a generated artifact,
tangled from `files/spacemacs/init.org`, and will be silently overwritten
on the next tangle. The file itself carries this warning as a comment.
Always edit `init.org` instead.

## File locations

| Path | Role |
|---|---|
| `files/spacemacs/init.org` | Literate source of truth. Edit this. |
| `files/spacemacs/init.el` | Generated by tangle. Never hand-edit. |
| `files/spacemacs/private/layers/*/packages.el`, `config.el`, `funcs.el` | Hand-written custom layers. Edit directly, no tangle. |

Justfile chain: `just emacs-literate` tangles `init.org` -> `init.el`,
byte-compiles it, then chains (via `&&`) into the private
`validate-spacemacs-layers` recipe, which byte-compiles every file under
`private/layers/`. `emacs-setup` and `up-spacemacs-to` both depend on
`emacs-literate`, so they inherit all of this validation transitively.

`validate-spacemacs-layers` is `[private]` (hidden from `just --list`) but
fully invokable standalone: `just validate-spacemacs-layers`. Use it
directly when only a layer file changed and `init.org` was untouched.

## Workflow: design check (before editing)

Before proposing where/what to change, check three sources for existing
coverage, so a custom layer or hand-written elisp isn't proposed for
something Spacemacs already ships or something already solved locally:

1. **Bundled Spacemacs catalog**: `~/.config/emacs/layers/**` (materialized
   by `just emacs-setup` from the Nix-locked source, organized under
   category prefixes like `+lang`, `+tools`, `+checkers`). Search here
   first for a stock layer matching the request (language support, a
   tool integration) before proposing custom elisp. No existence check
   on this path — if `emacs-setup` was never run on this machine, the
   search simply finds nothing there, same as any other empty directory.
2. **Currently enabled layers**: `dotspacemacs-configuration-layers` in
   `init.org` — is something already turned on that covers this?
3. **Existing custom layers**: `files/spacemacs/private/layers/*` — has
   this already been solved locally?

Also grep `init.org` and relevant `private/layers/*.el` files for
existing definitions that might conflict with the request:

- Keybindings: `set-leader-keys`, `define-key`
- Packages: `use-package`, layer package lists
- Variables: `setq`, `custom-set-variables`

Surface any hits to the user before committing to a specific insertion
point. Don't silently duplicate or shadow existing config.

## Workflow: placement discovery (init.org only)

`init.org` has a `* Table of contents :TOC:` heading near the top
(auto-maintained by org on save) listing every heading with its nesting
depth. Read that block first to find where the new content belongs.

- If a heading matches the topic, insert there.
- If nothing matches, nest a new subsection under the closest relevant
  top-level heading. Never blind-append to the end of the file.
- The TOC entry itself goes stale until the file is next saved in Emacs.
  Do not hand-edit the TOC — org regenerates it on save.

## Workflow: structural edit safety (init.org only)

These are all currently non-issues in this file. Keep it that way:

- Tangle fully regenerates `init.el` from every matching block in
  document order on every run — it is not an incremental patch. A
  mistake anywhere affects the whole regenerated file.
- Preserve exact heading-level asterisk counts when nesting or moving
  content. Miscounting silently reparents content under the wrong
  heading and can change inherited context.
- Never insert content between a headline and its `:PROPERTIES:` drawer,
  and never create a second drawer for the same headline. Both are
  silent corruption, not parse errors.
- Keep `#+begin_src` / `#+end_src` boundaries balanced. Never let an
  edit span across an existing block's boundary.
- Any example/illustrative code block added for documentation purposes
  only must be tagged `:tangle no` explicitly. The file-level property
  (`:tangle init.el`) is inherited by every block by default.
- This file currently has no noweb references (`<<...>>`) and no
  `Local Variables: eval:` footer. If either is ever introduced, treat
  it as high-risk and flag it explicitly rather than assuming
  batch-mode Emacs behaves like an interactive session.

## Workflow: comment discipline (init.org only)

Elisp comments inside `init.org` code blocks: 1-2 lines max, terse.
Longer explanations go in org prose, not in elisp comments — as a
sub-subsection titled "Notes", one level deeper than the code block's
heading, placed immediately after it. This rule does not apply to
`private/layers/*.el`, which have no org-prose escape hatch.

## Workflow: editing init.org

1. Run the design check and placement discovery above.
2. Edit `init.org`.
3. Run `just emacs-literate`. It self-validates: checks `emacs` is on
   PATH, tangles, byte-compiles the generated `init.el`, then chains
   into `validate-spacemacs-layers`.
4. Trust the exit code. On failure, surface the recipe's error message
   verbatim — it already identifies whether the failure was a missing
   `emacs` binary, a failed byte-compile of `init.el`, or a failed
   layer file.
5. Do not restart or reload the emacs daemon. Leave that to the user.

## Workflow: editing a private layer

1. Edit the relevant file under `files/spacemacs/private/layers/`.
2. No tangle needed — these files are hand-written, not generated, and
   take effect on the next Emacs/Spacemacs load. `just emacs-literate`
   is irrelevant here.
3. Cross-check that the layer's name appears in
   `dotspacemacs-configuration-layers` inside `init.org`. If the layer
   is edited but not registered there, **do not mark the task
   complete**. Either ask the user whether to register it, or get an
   explicit dismissal from them first.
4. Validate with `just validate-spacemacs-layers` (standalone,
   byte-compiles every layer file in one pass).

## Workflow: daemon status check (diagnostic only)

Both NixOS and Darwin run a persistent emacs daemon/server, connected to
via `emacsclient`. Use these only to diagnose connection issues — never
to restart, reload, or otherwise mutate the daemon:

- NixOS: `systemctl --user status emacs.service` and
  `systemctl --user status emacs.socket` (socket-activated).
- Darwin: `launchctl print gui/$(id -u)/<label>` (check the plist under
  `~/Library/LaunchAgents/` for the exact label).

## Limitations

- Byte-compile checks validate syntax only, not semantic correctness
  (e.g. a new keybinding silently shadowing an existing one beyond what
  the design-check grep catches).
- The design-check grep is naive/pattern-based, not full static
  analysis.
- Live-buffer conflicts (editing a file the daemon has open with
  unsaved changes) are not handled by this skill. Emacs's own
  file-changed-on-disk detection is relied on instead.
